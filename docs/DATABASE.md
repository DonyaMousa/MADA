| --- | --- | --- |

New imports default to `unverified_import`, replacing the development-example default. Publication requires `verification_state = 'verified'`, a verification date, and a non-example data label. This prevents a development placeholder or unreviewed import from appearing as a live listing. No scholarship data is seeded by this migration.

Search uses PostgreSQL's `simple` text-search configuration for English and Arabic tokens. It does not provide Arabic morphology or semantic search. Existing title/provider trigram search remains available. `search_vector` is database generated.

## Security findings and corrections

1. **Initial schema creation and anonymous reads:** `private.is_admin()` originally referenced `user_roles` before the table existed. Its execution/schema grants also did not cover anonymous policies that called it. The table now precedes the function; anonymous and authenticated roles can invoke this narrowly scoped helper. Its definer function has an empty search path and reads database-owned roles, never user metadata.
2. **Cross-user references:** an owner-only policy on a child row did not establish ownership of its referenced application, document, letter or conversation. Composite foreign keys now require the same user. Optional application links also require the same scholarship. Community replies require the same scholarship and channel. These constraints apply even to service-role writes.
3. **Frontend-generated AI output:** users could originally write their own SOP feedback and assistant messages of either role, along with extracted text and CV suggestions. SOP reviews, CV extractions, matches, extraction text and profile CV suggestions are now service-managed. Students can insert only `user` assistant messages, with empty citations; submitted messages are immutable.
4. **Overbroad grants:** blanket browser table/sequence privileges were replaced with explicit operations and editable-column lists. Identity, ownership, context, provenance and model fields cannot be reassigned through ordinary browser updates. Default grants for future objects created by the migration role are restricted too; future migrations must still define grants and RLS explicitly.
5. **Role elevation:** the original role table already lacked browser write policies. This protection remains, with browser writes also revoked at the privilege layer. New-account metadata cannot select an admin role. Administrator assignment remains a trusted database operation.
6. **Document privacy:** profiles, document metadata, CV extractions, matches, SOP output and conversations are owner-readable. Being an application admin does not grant access to other students' profiles, documents, AI output or delivery logs. Operational code using `service_role` remains privileged and must authorize every request.
7. **Forged notifications and operational records:** students can only read their notifications and update `read`. Import runs, sources, reminder delivery records and audit logs cannot be written from the browser. Provider proposals must begin at `pending_review`, and clients cannot supply their status during insertion.
8. **Community exposure:** students cannot enumerate everyone else's memberships, post without membership, report inaccessible posts, or link a reply to another scholarship/channel. Community row identities and context are immutable through browser updates.
9. **Data API exposure:** local `supabase/config.toml` exposes only `public`; `storage` was removed from the PostgREST schema list. Storage continues through the Storage API. No hosted configuration was changed. Check the hosted project's exposed schemas separately before launch.

## Storage and lifecycle boundaries

The `documents` bucket retains its ID/name, private setting, 10 MiB limit, original MIME allowlist and all four original owner-folder Storage policies. On an existing bucket, the migration reasserts the private setting and limits without replacing files. Object paths must begin with the authenticated user's UUID. Metadata paths are unique, owner-prefixed and exclude traversal segments/backslashes.

Upload through the Storage API first, then register the `documents` row. Document path, size, MIME declaration and kind cannot be reassigned by a browser after registration. Students may rename display fields. Storage uploads/updates/deletes retain their existing owner-only policies.

Deleting document metadata cascades its CV extractions, dependent matches and attachments. Database cascades do not remove Storage bytes. Deleting or replacing a Storage object alone also does not automatically update application metadata or derived AI records. The future trusted deletion/reprocessing workflow must coordinate both systems, remove obsolete `documents.extracted_text`/`profiles.cv_extracted_suggestions`, and validate actual file bytes/hash before using extraction results. MIME declarations are not file-content validation. No Storage-table deletion trigger or file-processing service was added.

The existing `docs/PRIVACY.md` describes intended product lifecycle behavior; these coordinated deletion operations still need implementation. Signed URLs and account/file cleanup require the future application service. A database migration cannot enforce signed-link expiration or scan uploads.

## Result and worker contracts

- `matches` stores the latest result through a service upsert on `(user_id, scholarship_id)`. It is not a full calculation-history table. Preserve exact input/model versions in every result. Compare `profile_updated_at` and `scholarship_updated_at` against current rows before using cached results; the input fingerprint must include relevant document content and algorithm configuration. Deleting an extraction removes matches that reference it.
- `eligibility_results` is an array of rule outcomes/evidence. `score_breakdown` is an object of components, raw/normalized values, weights and contributions. `explanation` contains the human-readable reasons and missing inputs. `model_versions` identifies all models/prompts used. JSON container types are constrained; the future worker must validate each version's internal JSON schema and arithmetic. No score formula or model is implemented here.
- `cv_extractions` retains separate processing attempts linked to the original document and user. Its versioned structured data contains suggestions; applying confirmed values uses normal editable profile fields. A trusted worker manages status transitions, verifies content hashes and avoids sending another user's file to an extractor.
- Imports write `scholarship_sources`, then `fetch_runs`, then provenance-linked scholarship records. `(source_id, source_record_id)` deduplicates records where a source supplies a stable ID. Fetch runs must belong to the listing's recorded source. Source URLs are provenance, not permission to fetch arbitrary URLs; the future importer needs its own fetch controls. Error details must exclude credentials and private student data.
- Deadline workers must use the canonical scholarship deadline, respect reminder preferences/timezones and use the unique delivery key `(user_id, scholarship_id, channel, deadline_at, reminder_days)`. `scheduled_for`, retry fields and `sent_at` support a future scheduler. Rows do not send email or create in-app messages automatically. Reconcile queued reminders if deadlines/preferences change; use `notifications.delivery_key` for idempotent in-app creation.
- Database triggers maintain `updated_at`, validate timezone names and clear document attachment opt-in when an application's optional conversation reference is removed. No cron tasks or external network functions are installed.

Additional constraints cover GPA/scale, graduation years, progress, document size/types/paths, JSON container types, HTTP(S) listing URLs, processing timestamp/state coherence, score bounds and import counters. Foreign keys have supporting indexes, including the new composite ownership relationships.

## Commands to apply

Run from `C:\Users\msi\Desktop\MADA` using the installed CLI. No reset is needed.

For a fresh local Supabase stack after installing and starting Docker Desktop:

```powershell
npx --no-install supabase start
npx --no-install supabase migration up --local
npx --no-install supabase db lint --local --schema public,private --fail-on warning
```

`start` normally applies migrations on first initialization; `migration up --local` applies any remaining pending versions. For an existing local stack with application tables, use a separate development project/directory rather than a reset or applying this consolidated initial schema over existing tables.

Generate types from that local stack without overwriting the checked-in file on command failure:

```powershell
$databaseTypes = & npx.cmd --no-install supabase gen types typescript --local --schema public
if ($LASTEXITCODE -ne 0) { throw 'Supabase type generation failed' }
$databaseTypes | Set-Content -Encoding utf8 supabase/types/database.types.ts
```

For the hosted project, **only after deployment approval**, authenticate/link and inspect migration history:

```powershell
npx --no-install supabase login
npx --no-install supabase link --project-ref YOUR_PROJECT_REF
npx --no-install supabase migration list --linked
npx --no-install supabase db push --linked --dry-run --skip-vault
```
